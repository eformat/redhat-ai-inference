== Overview

In this module you deploy a model for inference on Red Hat AI Enterprise.
You select a validated open-source model, configure a model server backed
by an NVIDIA GPU, and verify the deployment is accepting inference
requests. The model and runtime you configure here are the foundation for
the rest of the lab: they carry forward unchanged through every subsequent
module.

.Duration
10 minutes (3 min explore / 5 min deploy / 2 min verify)

.Prerequisites
Module 0: Getting Connected — you are logged in to the Red Hat AI
Enterprise console with your lab credentials and know how to reach the
OpenShift AI dashboard.

toc::[]

== Learning objectives

* Deploy a model for inference on Red Hat AI Enterprise
* Verify that the deployed model is running and accepting inference requests

Along the way you also review the available model server runtimes, select a
model from the model catalog, configure model server parameters — runtime,
replicas, and resource limits — and confirm the model responds to a test
inference request.

=== Project and namespace layout

The model you deploy in this module runs in your own project, named after
your lab user — for example, `lab-user-dev`. Everything you create in the
next sections lives in that project:

* The model server deployment and its `LLMInferenceService` resource
* The pod that runs the vLLM serving image on the GPU node
* The token secret generated for inference requests

Platform-level components — the serving runtime templates, operators, and
the DataScienceCluster configuration — are managed by the cluster
administrator and run outside your project.

Your lab user has no project yet. Create it from the OpenShift AI
dashboard:

. In the dashboard left menu, click *Projects*. The Projects page opens
with no projects listed.
. Click *Create project*.
. In the *Name* field, enter `lab-user-dev`.
. Optional: enter a *Description*.
. Click *Create*. Your project opens in the dashboard.

[NOTE]
====
Create the project from the dashboard rather than with `oc new-project` —
the dashboard adds the OpenShift AI labels that make the project visible on
the *Projects* page and selectable in the deploy wizard later in this
module.

== Exercise 2: Deploy the model for inference

Now that you have confirmed the environment is ready, you will deploy the
model for inference.

=== Select the model

Red Hat AI ships models at two support levels: *validated* and *enabled*.
Red Hat tests validated models with GuideLLM performance benchmarking and
Language Model Evaluation Harness accuracy evaluations across specific
OpenShift Container Platform, Red Hat OpenShift AI, and Red Hat AI
Inference version combinations, and ships them with quantized variants in
formats such as FP8 and BF16.

For this lab you use *NVIDIA Nemotron Nano 9B v2 FP8-dynamic*, a validated,
instruction-tuned large language model designed for enterprise deployment.
The FP8 quantization keeps the memory footprint low: the validated model
support matrix lists a minimum of roughly 11.6 GB of VRAM, so the model fits
on a single 24 GB NVIDIA L4 GPU node with plenty of headroom for the
attention key-value cache. It delivers production-grade inference
performance for coding assistance, reasoning tasks, and tool-calling
workflows, which makes it ideal for Model-as-a-Service architectures where
multiple teams share centrally-managed model infrastructure.

You can discover and select verified generative AI models in the OpenShift
AI *model catalog* — a curated, user-facing directory for finding models
appropriate for your business use case.

=== Deploy the model from the catalog

To deploy the model on the single-model serving platform (KServe), GPU
support must be enabled on the cluster and the Node Feature Discovery
Operator must be installed and configured. Both are already set up in the
lab environment.

. In the OpenShift AI dashboard left menu, click *AI hub*, then *Models*.
The *Catalog* tab opens, listing the models available to your organization.
. In the search field, enter `nemotron` and press *Enter*. The Nemotron
model family appears.

. Click the *NVIDIA-Nemotron-Nano-9B-v2-FP8-dynamic* model card. The model
detail page opens with the model's description, performance insights, and
safety and security insights.

image::101-catalog-model-card.png[Model catalog page for NVIDIA-Nemotron-Nano-9B-v2-FP8-dynamic with the Deploy model button,link=self,window=blank,width=700]

. Click *Deploy model*. The Deploy a model wizard opens.
. In the *Preconfigure deployment* step, select your project
(`lab-user-dev`) and click *Next*.
. In the *Model details* step, the model location and model type are
imported from the model catalog and shown read-only. The wizard points the
deployment at the validated Nemotron Nano 9B v2 FP8-dynamic modelcar — an
OCI-compliant registry image whose filesystem holds the model weights, so
the serving engine loads it directly from the image. The lab environment
pre-pulls the model and serving images, which keeps startup time short.
Click *Next*.

image::101-wizard-model-details.png[Model details step with the model location imported from the model catalog,link=self,window=blank,width=700]

. In the *Model deployment* step, configure the deployment:
.. In the *Model deployment name* field, enter `nemotron-nano-9b-v2`.
.. In the *Description* field, enter a short description of the deployment.
.. Select the *GPU serving (NVIDIA GPU)* hardware profile. The profile
provides the CPU, memory, and GPU resource baseline for the deployment.
.. From the *Accelerator configuration* list, select *vLLM NVIDIA GPU Single
Node*. The configuration carries the GPU node toleration so the model
server pod can schedule on the GPU node.
.. Keep the *Replica count* at `1`.
.. Click *Next*.

image::101-wizard-deployment.png[Model deployment step with the GPU serving hardware profile and the accelerator configuration,link=self,window=blank,width=700]

. In the *Advanced settings* step:
.. Optional: select *Add as AI asset endpoint* (tech preview) to publish
the model's endpoint on the *AI asset endpoints* page and make it testable

.. Leave *Publish as MaaS* cleared — publishing the model through the MaaS
gateway is covered in Module 3.
.. Keep *Token authentication* enabled and enter `model-tester` in the
*Service account name* field. The actual tokens are created and displayed

--max-model-len=131072
--reasoning-parser nemotron_v3
----

=== What the wizard creates

Behind the scenes, the wizard creates an `LLMInferenceService` resource on
the single-model serving platform (KServe), named after the model from the
catalog. The resource shown here is the configuration used in this lab, simplified
for readability:

[source,yaml]
----
apiVersion: serving.kserve.io/v1alpha2
kind: LLMInferenceService
metadata:
  name: redhatainvidia-nemotron-nano-9 # <1>
  namespace: lab-user-dev
  annotations:
    opendatahub.io/hardware-profile-name: gpu-serving
  labels:
    kueue.x-k8s.io/queue-name: default # <2>
    opendatahub.io/dashboard: "true"
    opendatahub.io/genai-asset: "true"
spec:
  baseRefs:
    - name: redhatainvidia-nemotron-nano-9 # <3>
  model:
    name: redhatainvidia-nemotron-nano-9
    uri: oci://registry.redhat.io/rhelai1/modelcar-nvidia-nemotron-nano-9b-v2-fp8-dynamic:1.5 # <4>
  replicas: 1 # <5>
  router:
    gateway: {} # <6>
    route: {}
  template:
    containers:
      - name: main
        env:
          - name: VLLM_ADDITIONAL_ARGS # <7>
            value: >-
              --trust-remote-code
              --max-model-len=131072
              --reasoning-parser nemotron_v3
        resources: # <8>
          requests:
            cpu: "2"
            memory: 16Gi
            nvidia.com/gpu: "1"
          limits:
            cpu: "2"
            memory: 16Gi
            nvidia.com/gpu: "1"
----

<1> *Model-derived name* -- The wizard names the service after the model from
the catalog, truncated to fit Kubernetes naming rules.
<2> *Kueue queue* -- Places the deployment in the project's Kueue queue, so the
model server is scheduled within the cluster's GPU quota.
<3> *Accelerator configuration reference* -- Points at the
`LLMInferenceServiceConfig` the wizard created from the accelerator
configuration you selected (shown below).
<4> *Modelcar URI* -- The validated model ships as an OCI image; the serving
engine loads the weights directly from the image filesystem.
<5> *Replica* -- One model server replica, holding one GPU. Scaling replicas
out for shared consumption is covered in Module 3.
<6> *Gateway routing* -- The KServe controller attaches the model's HTTPRoute
to the `openshift-ai-inference` gateway, which terminates TLS and serves the
model's route over HTTPS.
<7> *Runtime arguments* -- The custom arguments you added in Advanced settings,
passed to vLLM through the `VLLM_ADDITIONAL_ARGS` environment variable.
`--trust-remote-code` allows the model's custom code (Mamba-hybrid
architecture); `--max-model-len=131072` sets a 131,072-token context window;
`--reasoning-parser nemotron_v3` separates the model's thinking from its final
answer in API responses — the parser is built into the vLLM image, so no
plugin is needed.
<8> *Resource baseline* -- Requests and limits from the GPU serving hardware
profile: 2 CPU, 16 Gi memory, and 1 GPU, sized for the Nemotron model on a
single NVIDIA GPU node.

The `baseRefs` entry points at an `LLMInferenceServiceConfig` the wizard
creates alongside the service — it carries the GPU node toleration from the
accelerator configuration you selected:

[source,yaml]
----
apiVersion: serving.kserve.io/v1alpha2
kind: LLMInferenceServiceConfig
metadata:
  name: redhatainvidia-nemotron-nano-9
spec:
  template:
    tolerations:
      - effect: NoSchedule
        key: nvidia.com/gpu # <1>
        operator: Equal
        value: l4-gpu
----

<1> *GPU node toleration* -- Lets the model server pod schedule on the GPU
node, which is tainted `nvidia.com/gpu=l4-gpu:NoSchedule` by the NVIDIA GPU
operator.

=== Send a test inference request

The vLLM runtime is compatible with the OpenAI REST API, so the model
serves the `/v1/chat/completions` path. The model serving platform serves
API requests over the HTTPS port of the inference gateway (usually
port 443).

Store the endpoint and token as shell variables, then send a chat request.
First, the endpoint URL from the `LLMInferenceService`:

[source,bash,role="execute"]
----
MODEL_URL=$(oc get llminferenceservice redhatainvidia-nemotron-nano-9 -o jsonpath='{.status.url}')
echo "MODEL_URL: $MODEL_URL"
----

Then the token from the service account secret the deployment created:

[source,bash,role="execute"]
----
TOKEN=$(oc get secret model-tester-redhatainvidia-nemotron-nano-9-sa -o jsonpath='{.data.token}' | base64 -d)
echo "TOKEN: ${TOKEN:0:12}..."
----

Finally, send a chat request:

[source,bash,role="execute"]
----
curl -s $MODEL_URL/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "model": "redhatainvidia-nemotron-nano-9",
    "messages": [
      {
        "role": "user",
        "content": "In one sentence, what is Model as a Service?"
      }
    ],
    "max_tokens": 3072
  }' | jq .
----

A successful response returns the assistant's answer in the
OpenAI-compatible chat completion format. Because the deployment includes
the `--reasoning-parser nemotron_v3` argument, the model's thinking is
returned in a separate `reasoning` field, and `content` holds only the
final answer (abbreviated for readability):

----
{
  "id": "chatcmpl-f584f9ba-8c56-4567-a050-bd82afda14cc",
  "object": "chat.completion",
  "created": 1793069237,
  "model": "redhatainvidia-nemotron-nano-9",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "reasoning": "Okay, the user is asking for a one-sentence explanation of \"Model as a Service.\" Let me start by breaking down the term. \"Model\" here likely refers to machine learning models. \"Service\" suggests a cloud-based or API-driven offering...",
        "content": "Model as a Service is a cloud-based platform that provides pre-trained machine learning models via APIs, enabling users to deploy, manage, and scale AI solutions without building models from scratch."
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 23,
    "completion_tokens": 325,
    "total_tokens": 348
  }
}
----

. Confirm the response contains a `choices` array with the assistant's
message in `choices[0].message.content`.
. Keep the endpoint URL and token saved — you will reuse them when you
expose the model as a Model-as-a-Service in Module 3.

Your model is now deployed, running, and accepting inference requests — the
foundation for every module that follows.
