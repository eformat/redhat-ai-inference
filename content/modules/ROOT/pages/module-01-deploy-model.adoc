== Overview

In this module you deploy a model for inference on Red Hat AI Enterprise.
You select a validated open-source model, configure a model server backed
by an NVIDIA GPU, and verify the deployment is accepting inference
requests. The model and runtime you configure here are the foundation for
the rest of the lab: they carry forward unchanged through every subsequent
module.

.Duration
10 minutes (3 min explore / 5 min deploy / 2 min verify)

.Prerequisites
Module 0: Getting Connected — you are logged in to the Red Hat AI
Enterprise console with your lab credentials and know how to reach the
OpenShift AI dashboard.

toc::[]

== Learning objectives

* Deploy a model for inference on Red Hat AI Enterprise
* Verify that the deployed model is running and accepting inference requests

Along the way you also review the available model server runtimes, select a
model from the model catalog, configure model server parameters — runtime,
replicas, and resource limits — and confirm the model responds to a test
inference request.

=== Project and namespace layout

The model you deploy in this module runs in your own project, named after
your lab user — for example, `lab-user-dev`. Everything you create in the
next sections lives in that project:

* The model server deployment and its `LLMInferenceService` resource
* The pod that runs the vLLM serving image on the GPU node
* The token secret generated for inference requests

Platform-level components — the serving runtime templates, operators, and
the DataScienceCluster configuration — are managed by the cluster
administrator and run outside your project.

== 1.2 — Deploy the model for inference

=== Select the model

Red Hat AI ships models at two support levels: *validated* and *enabled*.
Red Hat tests validated models with GuideLLM performance benchmarking and
Language Model Evaluation Harness accuracy evaluations across specific
OpenShift Container Platform, Red Hat OpenShift AI, and Red Hat AI
Inference version combinations, and ships them with quantized variants in
formats such as FP8 and BF16.

For this lab you use *NVIDIA Nemotron 3 Nano 30B A3B FP8*, a validated,
instruction-tuned large language model designed for enterprise deployment.
The FP8 quantization keeps the memory footprint low: the validated model
support matrix lists a minimum of roughly 37.6 GB of VRAM, so the model
fits on a single 48 GB NVIDIA L40S GPU node. It delivers production-grade
inference performance for coding assistance, reasoning tasks, and
tool-calling workflows, which makes it ideal for Model-as-a-Service
architectures where multiple teams share centrally-managed model
infrastructure.

You can discover and select verified generative AI models in the OpenShift
AI *model catalog* — a curated, user-facing directory for finding models
appropriate for your business use case.

=== Deploy through the model serving wizard

To use the vLLM NVIDIA GPU ServingRuntime for KServe, GPU support must be
enabled on the cluster and the Node Feature Discovery Operator must be
installed and configured. Both are already set up in the lab environment.

. In the OpenShift AI dashboard left menu, click *Projects*.
. Click the name of your project. The project details page opens.
. Click the *Deployments* tab.
. Click *Deploy model*. The Deploy a model wizard opens.
. In the *Model details* section, provide information about the model:
.. From the *Model location* list, select the connection type that points
to the Nemotron 3 Nano 30B A3B FP8 modelcar (an OCI-compliant registry
image) and complete the connection detail fields.
.. From the *Model type* list, select *Generative AI model*.
.. Click *Next*.
. In the *Model deployment* section, configure the deployment:
.. In the *Model deployment name* field, enter `nemotron-3-nano-30b-a3b`.
.. In the *Description* field, enter a short description of the deployment.
.. From the *Hardware profile* list, select the profile that exposes one
NVIDIA GPU. Selecting an NVIDIA GPU accelerator filters for compatible
runtimes such as the vLLM NVIDIA GPU ServingRuntime for KServe.
.. Optional: click *Customize resource requests and limits* and set the
values listed in the configuration table below.
.. In the *Serving runtime* field, select *vLLM NVIDIA GPU ServingRuntime
for KServe*. If the system can identify a single distinct runtime for the
selected accelerator, the auto-select option picks it for you.
.. In the *Number of model server replicas to deploy* field, enter `1`.
.. Click *Next*.
. In the *Advanced settings* section:
.. Optional: select *Add as AI asset endpoint* to publish the model's
endpoint on the *Gen AI studio → AI asset endpoints* page, and enter `chat`
in the *Use case* field.
.. Optional: select *Model access* to make the model available through an
external route.
.. Select *Require token authentication* and enter a service account name,
for example `model-tester`. You use the generated token in section 1.3.
.. In the *Deployment strategy* section, select *Rolling update*.
. Click *Deploy*.

Verification: the deployed model appears on the *Deployments* tab of your
project and on the *Deployments* page of the dashboard with a checkmark in
the *Status* column.

=== What the wizard creates

Behind the scenes, the wizard creates an `LLMInferenceService` resource on
the single-model serving platform (KServe). The resource shown here is the
configuration used in this lab, simplified for readability:

[source,yaml]
----
apiVersion: serving.kserve.io/v1alpha1
kind: LLMInferenceService
metadata:
  name: nemotron-3-nano-30b-a3b
  namespace: lab-user-dev
  annotations:
    openshift.io/display-name: NVIDIA Nemotron 3 Nano 30B A3B FP8
    opendatahub.io/model-type: generative
    security.opendatahub.io/enable-auth: "true"
  labels:
    opendatahub.io/dashboard: "true"
    opendatahub.io/genai-asset: "true"
spec:
  model:
    name: nemotron-3-nano-30b-a3b
    uri: oci://registry.redhat.io/rhai/modelcar-nvidia-nemotron-3-nano-30b-a3b-fp8:3.0
  replicas: 1
  template:
    containers:
      - name: main
        image: registry.redhat.io/rhaii/vllm-cuda-rhel9:3.5.1
        command:
          - python
          - -m
          - vllm.entrypoints.openai.api_server
        args:
          - --model=/mnt/models
          - --served-model-name=nemotron-3-nano-30b-a3b
          - --max-model-len=131072
          - --enable-auto-tool-choice
          - --tool-call-parser=qwen3_coder
          - --trust-remote-code
          - --reasoning-parser-plugin=/mnt/models/nano_v3_reasoning_parser.py
          - --reasoning-parser=nano_v3
        resources:
          requests:
            cpu: "2"
            memory: 16Gi
            nvidia.com/gpu: "1"
          limits:
            cpu: "4"
            memory: 24Gi
            nvidia.com/gpu: "1"
    tolerations:
      - effect: NoSchedule
        key: nvidia.com/gpu
        operator: Equal
        value: l40-gpu
----

[[resource-config]]
.Model server configuration explained
[cols="1,2", options="header"]
|===
| Field | Purpose

| `spec.model.uri`
| Points to the validated Nemotron 3 Nano 30B A3B FP8 modelcar. The model
ships as a container image, so the serving engine loads it directly from
the image filesystem instead of downloading from remote object storage.

| `spec.replicas`
| One model server replica, holding one GPU. Scaling replicas out for
shared consumption is covered in Module 3.

| `spec.template.containers.image`
| The serving image, `rhaii/vllm-cuda-rhel9:3.5.1`, which runs the
OpenAI-compatible vLLM engine on NVIDIA GPUs.

| `resources`
| Requests of 2 CPU / 16 Gi memory / 1 GPU and limits of 4 CPU / 24 Gi
memory / 1 GPU, sized for the Nemotron model on a single L40S GPU node.

| custom runtime arguments (`args`)
| `--max-model-len=131072` sets a 131,072-token context window;
`--enable-auto-tool-choice` with `--tool-call-parser=qwen3_coder` enables
tool-calling; `--trust-remote-code` allows the model's custom code;
`--reasoning-parser-plugin` and `--reasoning-parser=nano_v3` enable the
Nemotron reasoning output parser shipped inside the modelcar.

| `tolerations`
| Lets the pod schedule on the GPU node, which is tainted
`nvidia.com/gpu=l40-gpu:NoSchedule`.
|===

====

=== Send a test inference request

The vLLM runtime is compatible with the OpenAI REST API, so the model
serves the `/v1/chat/completions` path. The model serving platform serves
external API requests over the HTTPS port of the OpenShift router (usually
port 443).

Store the endpoint and token as shell variables, then send a chat request:

[source,bash,role="execute"]
----
MODEL_URL=https://nemotron-3-nano-30b-a3b-lab-user-dev.apps.cluster.example.com
TOKEN=paste-your-token-secret-here

curl -s $MODEL_URL/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "model": "nemotron-3-nano-30b-a3b",
    "messages": [
      {
        "role": "user",
        "content": "In one sentence, what is Model as a Service?"
      }
    ]
  }'
----

A successful response returns the assistant's answer in the
OpenAI-compatible chat completion format:

----
{
  "id": "chatcmpl-4f9c8b3e",
  "object": "chat.completion",
  "created": 1761321600,
  "model": "nemotron-3-nano-30b-a3b",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "Model as a Service (MaaS) is a deployment model that provides access to pre-trained AI models through APIs, so you can consume model capabilities without managing the underlying infrastructure."
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 21,
    "completion_tokens": 38,
    "total_tokens": 59
  }
}
----

. Confirm the response contains a `choices` array with the assistant's
message in `choices[0].message.content`.
. Keep the endpoint URL and token saved — you will reuse them when you
expose the model as a Model-as-a-Service in Module 3.

Your model is now deployed, running, and accepting inference requests — the
foundation for every module that follows.

== Key takeaways

* Red Hat AI Enterprise provides a streamlined workflow for deploying models to inference endpoints.
* A deployed model must be verified before it can be evaluated or exposed to consumers.
* Model server configuration — runtime, replicas, and resource limits — determines how the model serves inference requests.
