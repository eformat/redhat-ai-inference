== Overview

In this module you deploy a model for inference on Red Hat AI Enterprise.
You select a validated open-source model, configure a model server backed
by an NVIDIA GPU, and verify the deployment is accepting inference
requests. The model and runtime you configure here are the foundation for
the rest of the lab: they carry forward unchanged through every subsequent
module.

.Duration
10 minutes (3 min explore / 5 min deploy / 2 min verify)

.Prerequisites
Module 0: Getting Connected — you are logged in to the Red Hat AI
Enterprise console with your lab credentials and know how to reach the
OpenShift AI dashboard.

toc::[]

== Learning objectives

* Deploy a model for inference on Red Hat AI Enterprise
* Verify that the deployed model is running and accepting inference requests

Along the way you also review the available model server runtimes, select a
model from the model catalog, configure model server parameters — runtime,
replicas, and resource limits — and confirm the model responds to a test
inference request.

=== Project and namespace layout

The model you deploy in this module runs in your own project, named after
your lab user — for example, `{project_namespace}`. Everything you create in the
next sections lives in that project:

* The model server deployment and its `LLMInferenceService` resource
* The pod that runs the vLLM serving image on the GPU node
* The token secret generated for inference requests

Platform-level components — the serving runtime templates, operators, and
the DataScienceCluster configuration — are managed by the cluster
administrator and run outside your project.

Your lab user has no project yet. Create it from the OpenShift AI
dashboard:

with no projects listed.
. Click *Create project*.
. In the *Name* field, enter `{project_namespace}`.
. Optional: enter a *Description*.
. Click *Create*. Your project opens in the dashboard.

== Exercise 2: Deploy the model for inference

Now that you have confirmed the environment is ready, you will deploy the
model for inference.

=== Select the model

Red Hat AI ships models at two support levels: *validated* and *enabled*.
Red Hat tests validated models with GuideLLM performance benchmarking and
Language Model Evaluation Harness accuracy evaluations across specific
OpenShift Container Platform, Red Hat OpenShift AI, and Red Hat AI
Inference version combinations, and ships them with quantized variants in
formats such as FP8 and BF16.

For this lab you use *GPT-OSS 20B (essential variant)*, a validated,
open-weight large language model designed for enterprise deployment.
The MXFP4 quantization keeps the memory footprint low: the model runs within
roughly 16 GB of memory, so it fits on a single 24 GB NVIDIA L4 GPU node with
plenty of headroom for the attention key-value cache. It delivers
production-grade inference performance for coding assistance, reasoning
tasks, and tool-calling workflows, which makes it ideal for
Model-as-a-Service architectures where multiple teams share centrally-managed
model infrastructure.

You can discover and select verified generative AI models in the OpenShift
AI *model catalog* — a curated, user-facing directory for finding models
appropriate for your business use case.

=== What the wizard creates

Behind the scenes, the wizard creates an `LLMInferenceService` resource on
the single-model serving platform (KServe), named after the model from the
catalog. The resource shown here is the configuration used in this lab, simplified
for readability:

[source,yaml,subs="specialcharacters,attributes"]
----
apiVersion: serving.kserve.io/v1alpha2
kind: LLMInferenceService
metadata:
  name: redhataigpt-oss-20b-essential # <1>
  namespace: {project_namespace}
  annotations:
    opendatahub.io/hardware-profile-name: gpu-serving
  labels:
    kueue.x-k8s.io/queue-name: default # <2>
    opendatahub.io/dashboard: "true"
    opendatahub.io/genai-asset: "true"
spec:
  baseRefs:
    - name: redhataigpt-oss-20b-essential # <3>
  model:
    name: redhataigpt-oss-20b-essential
    uri: oci://registry.redhat.io/rhai/modelcar-gpt-oss-20b-essential:3.0 # <4>
  replicas: 1 # <5>
  router:
    gateway: {} # <6>
    route: {}
  template:
    containers:
      - name: main
        env:
          - name: VLLM_ADDITIONAL_ARGS # <7>
            value: >-
              --enable-auto-tool-choice
              --tool-call-parser openai
        resources: # <8>
          requests:
            cpu: "2"
            memory: 16Gi
            nvidia.com/gpu: "1"
          limits:
            cpu: "2"
            memory: 16Gi
            nvidia.com/gpu: "1"
----

<1> *Model-derived name* -- The wizard names the service after the model from
the catalog, truncated to fit Kubernetes naming rules.
<2> *Kueue queue* -- Places the deployment in the project's Kueue queue, so the
model server is scheduled within the cluster's GPU quota.
<3> *Accelerator configuration reference* -- Points at the
`LLMInferenceServiceConfig` the wizard created from the accelerator
configuration you selected (shown below).
<4> *Modelcar URI* -- The validated model ships as an OCI image; the serving
engine loads the weights directly from the image filesystem.
<5> *Replica* -- One model server replica, holding one GPU. Scaling replicas
out for shared consumption is covered in Module 3.
<6> *Gateway routing* -- The KServe controller attaches the model's HTTPRoute
to the `openshift-ai-inference` gateway, which terminates TLS and serves the
model's route over HTTPS.
<7> *Runtime arguments* -- The validated tool-calling arguments the wizard
pre-populated from the model catalog, passed to vLLM through the
`VLLM_ADDITIONAL_ARGS` environment variable. `--enable-auto-tool-choice`
together with `--tool-call-parser openai` enables tool calling — GPT-OSS
handles reasoning and tool calls natively through its harmony response
format, and the `openai` tool-call parser is built into the vLLM image, so
the model's thinking is returned in a separate `reasoning` field and tool
calls in the OpenAI-compatible format without any additional parsers.
<8> *Resource baseline* -- Requests and limits from the GPU serving hardware
profile: 2 CPU, 16 Gi memory, and 1 GPU, sized for the GPT-OSS model on a
single NVIDIA GPU node.

The `baseRefs` entry points at an `LLMInferenceServiceConfig` the wizard
creates alongside the service — it carries the GPU node toleration from the
accelerator configuration you selected:

[source,yaml]
----
apiVersion: serving.kserve.io/v1alpha2
kind: LLMInferenceServiceConfig
metadata:
  name: redhataigpt-oss-20b-essential
spec:
  template:
    tolerations:
      - effect: NoSchedule
        key: nvidia.com/gpu # <1>
        operator: Equal
        value: l4-gpu
----

<1> *GPU node toleration* -- Lets the model server pod schedule on the GPU
node, which is tainted `nvidia.com/gpu=l4-gpu:NoSchedule` by the NVIDIA GPU
operator.

=== Send a test inference request

The vLLM runtime is compatible with the OpenAI REST API, so the model
serves the `/v1/chat/completions` path. The model serving platform serves
API requests over the HTTPS port of the inference gateway (usually
port 443).

Store the endpoint and token as shell variables, then send a chat request.
First, the endpoint URL from the `LLMInferenceService`:

[source,bash,role="execute"]
----
MODEL_URL=$(oc get llminferenceservice redhataigpt-oss-20b-essential -o jsonpath='{.status.url}')
echo "MODEL_URL: $MODEL_URL"
----

image::101-cli-endpoint.png[The terminal showing the model endpoint URL retrieved from the LLMInferenceService,link=self,window=blank,width=700]

Then the token from the service account secret the deployment created:

[source,bash,role="execute"]
----
TOKEN=$(oc get secret model-tester-redhataigpt-oss-20b-essential-sa -o jsonpath='{.data.token}' | base64 -d)
echo "TOKEN: ${TOKEN:0:12}..."
----

image::101-cli-token.png[The terminal showing the model authentication token as a short prefix,link=self,window=blank,width=700]

Finally, send a chat request:

[source,bash,role="execute"]
----
curl -s $MODEL_URL/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "model": "redhataigpt-oss-20b-essential",
    "messages": [
      {
        "role": "user",
        "content": "In one sentence, what is Model as a Service?"
      }
    ],
    "max_tokens": 3072
  }' | jq .
----

A successful response returns the assistant's answer in the
OpenAI-compatible chat completion format. GPT-OSS handles reasoning
natively through its harmony response format: the model's thinking is
returned in a separate `reasoning` field, and `content` holds only the
final answer:

image::101-cli-inference.png[The terminal showing the full chat completion response with the reasoning field and the final content answer,link=self,window=blank,width=700]

. Confirm the response contains a `choices` array with the assistant's
message in `choices[0].message.content`.
. Keep the endpoint URL and token saved — you will reuse them when you
expose the model as a Model-as-a-Service in Module 3.

Your model is now deployed, running, and accepting inference requests — the
foundation for every module that follows.
