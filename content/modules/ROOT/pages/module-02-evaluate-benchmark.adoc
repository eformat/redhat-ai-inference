== Overview

With a model deployed, you need to measure how well it performs before
exposing it to consumers. A model that has never been measured is a risk: you
cannot make serving decisions — expose, scale, or tune — without a quality
baseline. This module uses EvalHub, the evaluation service in Red Hat AI
Enterprise, to benchmark the model you deployed in Module 1: you run
evaluations from the CLI and the dashboard, analyze the scores, and make the
evaluation repeatable so you can track performance over time.

.Prerequisites
Module 1 completed — the model is deployed and serving inference requests.

.Duration
20 minutes (5 min setup / 7 min run / 4 min dashboard / 4 min compare)

== Learning objectives

* Run benchmark evaluations against a deployed model with the EvalHub CLI and
the OpenShift AI dashboard
* Analyze evaluation results and compare runs to track model performance over
time

== Exercise 1: Set up the EvalHub CLI

EvalHub runs each benchmark as an isolated job, tracks results through MLflow
experiment tracking, and exposes a versioned REST API with a matching CLI.
The lab's jumphost does not ship the CLI, so install it first.

=== Install the EvalHub CLI

[source,bash,role="execute"]
----
pip install --user eval-hub-sdk
evalhub --version
----

The CLI requires Python 3.11 or later.

=== Configure the CLI

Point the CLI at the lab's EvalHub service. The tenant is your project
namespace, and the token is your own OpenShift login token — the lab project
is registered as an EvalHub tenant, so your user token is all the
authorization you need:

[source,bash,role="execute"]
----
evalhub config set base_url https://evalhub-redhat-ods-applications.apps.ocp.ddrcj.sandbox4732.opentlc.com
evalhub config set tenant lab-user-dev
evalhub config set token $(oc whoami -t)
evalhub health
----

`evalhub health` should report the service as healthy.

=== Create the model authentication secret

Evaluations call your model's inference endpoint, which requires the
`Authorization: Bearer` token from Module 1. EvalHub reads model credentials
from a Kubernetes secret in your project — create one that holds the token
under the `api-key` key:

[source,bash,role="execute"]
----
TOKEN=$(oc get secret model-tester-redhatainvidia-nemotron-nano-9-sa -o jsonpath='{.data.token}' | base64 -d)
oc create secret generic model-auth --from-literal=api-key=$TOKEN
----

== Exercise 2: Run a benchmark evaluation

A *benchmark* measures a specific capability: `arc_easy` scores grade-school
science reasoning, `truthfulqa_mc1` scores resistance to common
misconceptions. Both run against the OpenAI-compatible endpoint of your
Module 1 model.

=== Submit the evaluation

Submit the evaluation with both benchmarks. The model URL is the gateway
endpoint from Module 1, and the tokenizer parameter tells the evaluation
runtime which tokenizer to use — the served model name is not a Hugging Face
identifier, so the runtime cannot infer it:

[source,bash,role="execute"]
----
MODEL_URL=$(oc get llminferenceservice redhatainvidia-nemotron-nano-9 -o jsonpath='{.status.url}')
evalhub eval run \
  --name nemotron-9-baseline \
  --model-url $MODEL_URL/v1 \
  --model-name redhatainvidia-nemotron-nano-9 \
  --provider lm_evaluation_harness \
  -b arc_easy -b truthfulqa_mc1 \
  --model-auth-secret model-auth \
  --experiment nemotron-9-eval \
  --param num_examples=10 \
  --param tokenizer=nvidia/NVIDIA-Nemotron-Nano-9B-v2
----

The server accepts the job and returns a job ID. Without the tokenizer
parameter the job fails with `not a valid model identifier listed on
huggingface.co` — always pass it for models served from a modelcar.

=== Monitor the run

Each benchmark runs as an isolated Kubernetes job in your project. Watch the
job progress:

[source,bash,role="execute"]
----
evalhub eval status
evalhub eval status --watch <job_id>
----

The job moves from `pending` (the pods are starting) to `running` to
`completed`. Ten examples per benchmark completes in about a minute once the
pods are up; larger samples take proportionally longer.

=== View the results

Retrieve the benchmark scores:

[source,bash,role="execute"]
----
evalhub eval results <job_id> --format table
----

----
BENCHMARK      PROVIDER               METRIC    VALUE
arc_easy       lm_evaluation_harness  acc       0.9
arc_easy       lm_evaluation_harness  acc_norm  0.7
truthfulqa_mc1 lm_evaluation_harness  acc       0.4
----

The `--format` flag supports `table`, `json`, `yaml`, and `csv`. The metrics
depend on the benchmarks you ran: `acc` and `acc_norm` are multiple-choice
accuracy (higher is better), `exact_match` scores math tasks. Ten examples
gives a quick signal with high variance — treat these numbers as a baseline,
not a verdict.

== Exercise 3: Run an evaluation from the dashboard

The OpenShift AI dashboard drives the same EvalHub service through the
*Evaluations* page.

=== Start an evaluation run

. In the OpenShift AI dashboard, click *Develop & train → Evaluations*. The
page lists the evaluation runs for the selected project.
+
image::201-evaluations-page.png[The Evaluations page listing evaluation runs with name, status, benchmarks evaluated, model, date and result,link=self,window=blank,width=700]

. Click *Start evaluation run*, select *Benchmark*, and pick `arc_easy` from
the benchmark catalog (245 benchmarks across 12 categories — filter by name
or category to find one).

. Fill the run configuration:
+
--
* *Evaluation name*: a unique name, such as `nemotron-9-recheck`.
* *MLflow experiment*: select *Select existing experiment* and choose the
experiment from Exercise 2 — results are logged as runs within it.
* *Evaluating*: *Model*, then *Choose model* and select *Other (External
endpoint)*.
* *Model name*: `redhatainvidia-nemotron-nano-9` (case-sensitive).
* *Endpoint URL*: the gateway endpoint from Exercise 2
(`$MODEL_URL/v1`).
* *Authentication secret name*: `model-auth`. Click *Validate connection* —
the dashboard confirms the model is reachable.
* *Benchmark parameters*: expand the section and enter the tokenizer, the
same parameter the CLI required:
+

[source,json]
----
{
  "num_examples": 10,
  "tokenizer": "nvidia/NVIDIA-Nemotron-Nano-9B-v2"
}
----
--
. Click *Start evaluation run*.
+
image::202-start-evaluation-run.png[The Start evaluation run form with the external endpoint configuration, validated connection and benchmark parameters,link=self,window=blank,width=700]

=== Monitor progress and view results

The evaluation appears in the runs list. Click the run name while it is
running to watch progress: the *Progress* tab shows each benchmark moving
from *In progress* to *Complete* with the elapsed time, and the *Events log*
tab streams the job's status events.

== Exercise 4: Compare runs and make it repeatable

A one-off benchmark is a data point; a repeatable evaluation workflow is a
baseline.

=== Compare two runs

. Run the evaluation a second time — from the CLI with a different
`num_examples`, or from the dashboard as in Exercise 3.
. On the *Evaluations* page, select the checkbox next to two completed runs
and click *Compare*. The comparison view opens the embedded MLflow interface:
a parallel-coordinates plot of parameters and metrics, with scatter, box, and
contour views available. Expand each run to see its configuration, and use
the filter to show only the parameters that differ.
+
image::204-run-comparison.png[The comparison view comparing two evaluation runs with a parallel coordinates plot,link=self,window=blank,width=700]

. The comparison view does not indicate whether a higher or lower metric
value is better — interpret changes using your knowledge of each benchmark
(`evalhub providers describe lm_evaluation_harness` lists every benchmark's
category and metrics).

=== Track results in MLflow

Every evaluation run is logged to its MLflow experiment. Open *Develop & train
→ Experiments*, select the experiment, and switch to *Evaluation runs*: each
benchmark's run appears with its metrics (`acc`, `acc_norm`,
`overall_score`), ready for side-by-side comparison across model versions and
configuration changes.

image::205-mlflow-experiments.png[The MLflow experiment page showing evaluation runs with metric columns,link=self,window=blank,width=700]

=== Save the evaluation as a config file

The evaluation can be expressed as a YAML file that you version and re-run
after any change — a new model version, different runtime arguments, or a
different serving configuration:

[source,yaml]
----
# evaljob.yaml — repeatable evaluation configuration
name: nemotron-9-baseline
model:
  url: https://inference-gateway.apps.ocp.ddrcj.sandbox4732.opentlc.com/lab-user-dev/redhatainvidia-nemotron-nano-9/v1
  name: redhatainvidia-nemotron-nano-9
  auth:
    secret_ref: model-auth
benchmarks:
  - provider_id: lm_evaluation_harness
    id: arc_easy
  - provider_id: lm_evaluation_harness
    id: truthfulqa_mc1
experiment:
  name: nemotron-9-eval
parameters:
  num_examples: 10
  tokenizer: nvidia/NVIDIA-Nemotron-Nano-9B-v2
----

Re-triggering the identical evaluation is then a single command:

[source,bash,role="execute"]
----
evalhub eval run --config evaljob.yaml
----

== Troubleshooting

* *Job fails with `not a valid model identifier listed on huggingface.co`* —
the tokenizer parameter is missing. Pass `--param
tokenizer=nvidia/NVIDIA-Nemotron-Nano-9B-v2` (CLI) or add it under
*Benchmark parameters* (dashboard).
* *Run stays `Pending` forever while the benchmark jobs complete* — the
project namespace is not registered as an evaluation tenant (the lab sets
the `evalhub.trustyai.opendatahub.io/tenant` and
`opendatahub.io/generated-namespace` labels; an administrator can re-apply
them with `oc label`).
* *Run marked `Failed` with `pod unschedulable` shortly after submission* —
the worker node was under disk pressure when the pods tried to start. The
jobs may recover on their own; re-run the evaluation once the node is
healthy (`oc get nodes` shows `DiskPressure` in the conditions).
* *`experiment ... is not active after create`* — an MLflow experiment with
that name was deleted; MLflow does not reuse deleted experiment names. Pick
a new experiment name.
* *MaaS gateway 4 MiB request-body limit (RHOAIENG-99765)* — evaluation
payloads routed through the gateway must stay under ~3.8 MB. Reduce
`num_examples`, trim the dataset, or point the endpoint directly at the
model's internal cluster endpoint.

== Module summary

**What you accomplished:**

* Installed and configured the EvalHub CLI against the lab's evaluation
service.
* Ran benchmark evaluations against the deployed model from the CLI and the
dashboard, and read the benchmark scores.
* Compared two runs in the MLflow comparison view and saved the evaluation as
a repeatable config file.

**Key takeaways:**

* EvalHub benchmarks a deployed model through isolated, parallel evaluation
jobs, with results tracked in MLflow.
* Benchmark scores are a baseline to compare against — interpret changes per
benchmark, since the comparison view does not flag metric direction.
* A repeatable evaluation config turns a one-off benchmark into a quality
gate you can re-run after every change.
