== Overview

The model is deployed, evaluated, exposed as a service, and connected to an application. This module brings those pieces together by validating the end-to-end request flow. You trace one inference request through the canonical serving chain — application → MaaS gateway → model server → model — verify every component along the way, troubleshoot a simulated failure, and confirm reliability against the baseline response captured at the start.

Structured, layer-by-layer log inspection is the core skill of this module: a shared AI service fails *between* layers, and the layer that stops logging is where the break is.

[NOTE]
====
Every failure introduced in this module is reversible — revert steps are explicit, and the environment must be left healthy for Module 6, which monitors the same serving chain under load.
====

.Prerequisites
Modules 1–4 complete — the model is deployed and serving (your project), exposed
as Model-as-a-Service with a reachable API endpoint, and the sample application
is deployed and connected to the model service.

.Duration
20 minutes (5 min trace / 5 min verify components / 5 min troubleshoot / 5 min confirm reliability)

== Learning objectives

By the end of this module you will be able to:

* Verify end-to-end request flow from application request to model response
* Troubleshoot common issues in the serving chain between the application and the model

== Exercise 1: Trace a request through the serving chain

.5 minutes

The path every successful inference follows:

----
[application]              [MaaS gateway]               [model server]
maas-chat-client --HTTP POST-->  maas-default-gateway  --HTTP-->  vLLM predictor  -->  [model]
      |                          |                          |
 application logs          istio-proxy log             predictor logs
----

The model behind the gateway is `redhataigpt-oss-20b-essential`, serving in your project (Module 1) and published to the `maas-default-gateway` gateway (Module 3). The consuming application is the one deployed in Module 4.

image::501-serving-chain.png[Annotated serving-chain diagram from application through MaaS gateway and model server to model,link=self,window=blank,width=700]

Send one request and follow it through every layer:

. Open the application interface and send a request that triggers an inference call. Note the response — this is your *baseline*. Copy it now: Exercise 4 compares against it to prove the chain is still healthy after the failure simulations.

. Inspect the application logs to confirm the outbound request was sent. Run
the `oc` commands in this module from your Dev Spaces terminal with
`lab-user-dev` as the current project (`oc project lab-user-dev` if you opened
a new terminal since Module 4):

[source,bash,role="execute"]
----
oc logs deployment/maas-chat-client --tail=20
----

Expected output (representative — exact wording depends on the application):

----
[INFO] inference request sent: POST https://maas.apps.<cluster-domain>/v1/chat/completions
[INFO] model service returned 200 OK (response saved)
----

Look for the `POST` to the MaaS gateway URL with a `200` status. The gateway URL was recorded in Module 3 and configured in Module 4.

image::502-app-logs.png[Application logs showing the outbound request to the MaaS gateway,link=self,window=blank,width=700]

. Inspect the MaaS gateway access log. The gateway runs as `data-science-gateway-class` pods with an `istio-proxy` container in the `openshift-ingress` namespace:

[source,bash,role="execute"]
----
oc logs -n openshift-ingress deployment/maas-default-gateway-data-science-gateway-class --tail=20
----

Expected output (abridged — one access-log line per request):

----
[2026-10-24T09:14:58.123Z] "POST /v1/chat/completions HTTP/1.1" 200 - via_upstream ...
----

The `200` with `via_upstream` confirms the gateway authenticated the request, applied the subscription policy, and forwarded it to the model server.

image::503-gateway-logs.png[Gateway istio-proxy access log with the 200 entry,link=self,window=blank,width=700]

. Inspect the model server logs to confirm the inference request was received and processed:

[source,bash,role="execute",subs="specialcharacters,attributes"]
----
MODEL_POD=$(oc get pods -n {project_namespace} -o name | grep '^pod/redhataigpt-oss-20b-essential-kserve' | head -1)
oc logs -n {project_namespace} ${MODEL_POD} --tail=20
----

Expected output (representative — exact wording varies by vLLM version):

----
INFO 10-24 09:14:57 [async_llm.py:258] Added request chatcmpl-<id>.
INFO 10-24 09:14:58 [logger.py:39] Finished request chatcmpl-<id>.
INFO:     10.129.4.27:41234 - "POST /v1/chat/completions HTTP/1.1" 200 OK
----

The `Added request` and `Finished request` lines confirm the model server received the request and the model processed it.

image::504-model-server-logs.png[Model server logs showing the request received and processed,link=self,window=blank,width=700]

[NOTE]
====
Set the values recorded in Module 3 as environment variables — later steps use them. Run these in the same terminal session so they remain available:

[source,bash,role="execute",subs="specialcharacters,attributes"]
----
export MAAS_URL="{maas_url}"
export MAAS_API_KEY="{maas_api_key}"
----
====

== Exercise 2: Verify each component

.5 minutes

Now that you have traced one request through every layer, you will verify
each component's health.

Work through the checklist layer by layer — each step gives the command and what healthy looks like.

. *Application pod Running and responding.* The pod deployed in Module 4 must be up:

[source,bash,role="execute"]
----
oc get pods -l app=maas-chat-client
----

Expected output:

----
NAME                            READY   STATUS    RESTARTS   AGE
maas-chat-client-7d9f8b6c5-xr2kp  1/1     Running   0          25m
----

Confirm the application interface still returns responses (send one as in Exercise 1).

. *MaaS subscription and API keys valid.* The subscription and authorization policy provisioned in Module 3 must both exist:

[source,bash,role="execute"]
----
oc get maassubscription,maasauthpolicy -n models-as-a-service
----

Expected output — both resources for each subscription tier (`maas-free-subscription` and `maas-premium-subscription`, each with a matching `-policy`). Then confirm your key authenticates — `/v1/models` lists the models your subscription grants:

[source,bash,role="execute"]
----
curl -s "${MAAS_URL}/v1/models" -H "Authorization: Bearer ${MAAS_API_KEY}" | jq -r '.data[] | [.id, .ready] | @tsv'
----

Expected output:

----
publishers/{project_namespace}/models/redhataigpt-oss-20b-essential   true
----

. *Gateway routing.* The gateway pods must be `Running`:

[source,bash,role="execute"]
----
oc get pods -n openshift-ingress | grep maas-default-gateway
----

Expected output:

----
NAME                                          READY   STATUS    RESTARTS   AGE
maas-default-gateway-istio-6f9b7d8c4-xq2lp    1/1     Running   0          2d
----

. *Model server Ready and serving.* The `LLMInferenceService` deployed in Module 1 (scaled to two replicas in Module 3) must report `READY`:

[source,bash,role="execute",subs="specialcharacters,attributes"]
----
oc get llminferenceservice redhataigpt-oss-20b-essential -n {project_namespace}
----

Expected output:

----
NAME                          URL   READY   AGE
redhataigpt-oss-20b-essential             True    45m
----

. *Metrics endpoints.* The model server exposes Prometheus metrics over HTTPS
on port `8000` at `/metrics` — the pod serves its own TLS certificate, hence
the `-k` below. Forward the port and scrape it:

[source,bash,role="execute",subs="specialcharacters,attributes"]
----
# Terminal 1 — forward the model server metrics port
oc port-forward -n {project_namespace} ${MODEL_POD} 8480:8000 2>&1 > /dev/null &

# Terminal 2 — scrape the endpoint (HTTPS — the pod serves its TLS cert)
curl -sk https://localhost:8480/metrics | grep vllm:num_requests_running
----

Expected output (vLLM metric series):

----
# HELP vllm:num_requests_running Number of requests in model execution batches.
# TYPE vllm:num_requests_running gauge
vllm:num_requests_running{engine="0",model_name="redhataigpt-oss-20b-essential"} 0.0
----

[NOTE]
====
The MaaS gateway also exposes Envoy telemetry metrics — the surface Module 6 consumes when monitoring serving behavior under load. If metrics are missing here, Module 6 will have nothing to display; fix metrics access before moving on.
====

. *Document the healthy trace.* Summarize what healthy looks like at each step — this is the reference you troubleshoot against in Exercise 3:

[cols="1,2,2"]
|===
|Layer |Evidence of health |Where you saw it

|Application
|`POST` to the gateway URL logged with `200`; response matches the interface
|`oc logs deployment/maas-chat-client`

|MaaS gateway
|Access-log line `200 via_upstream`; auth and subscription policy applied
|`oc logs -n openshift-ingress ... -c istio-proxy`

|Model server
|`Added request` / `Finished request` lines and `POST ... 200 OK`
|`oc logs -n \{project_namespace} ${MODEL_POD}`

|Model
|Completion returned with `finish_reason: stop` and token usage counts
|Application response body
|===

== Exercise 3: Troubleshoot a simulated failure

.5 minutes

Now that you know what healthy looks like at every layer, you will
introduce — and fix — a simulated failure.

Troubleshooting follows the same discipline: *introduce* a reversible failure, *observe* the error behavior in the logs, *diagnose* which layer broke, then *fix* and *revert*. The key diagnostic: a failure at one layer leaves the layers below it silent — if the model server logs show no request, the break is upstream at the gateway or the application.

[cols="1,2,2"]
|===
|Symptom |Broken layer |Covered in

|HTTP 401 / 403 on every request
|Access control — API key or subscription
|Scenario

|HTTP 404 or connection refused
|Wrong endpoint URL — check `MAAS_URL` against the value recorded in Module 3
|—

|HTTP 429 Too Many Requests
|Subscription token rate limit — wait for the window to reset and retry
|—
|===

=== Scenario — Invalid or expired API credential

.Introduce
Revoke the API key your application uses: in the OpenShift AI dashboard, navigate to *Gen AI studio → API keys*, and in the row for your key click the action menu (⋮) and select *Revoke*. Confirm by entering the key name. The key stops working — the application secret still holds the now-revoked key.

image::505-invalid-credential-401.png[API key revoke dialog on the API keys page,link=self,window=blank,width=700]

.Observe
Send a request from the application interface — it fails. Inspect the logs at each layer:

[source,bash,role="execute"]
----
oc logs deployment/maas-chat-client --tail=10
----

Expected output (representative):

----
HTTP 403: Forbidden — check your endpoint URL and API key
----

Check the model server — it is *silent*, because the gateway rejected the request before forwarding it:

[source,bash,role="execute",subs="specialcharacters,attributes"]
----
oc logs -n {project_namespace} ${MODEL_POD} --tail=10
----

No new `Added request` line appears: the model never saw the request.

.Diagnose
The layer that stopped logging is where the break is. A `401 Unauthorized` with `authentication_error` means the credential itself is invalid. The possible causes:

* *API key revoked* — exactly what you just did; create a new one
* *API key expired* — keys carry an expiration (30–90 days by default); create a new one from the API keys page
* *Incorrect key format* — the `Authorization: Bearer <key>` header must carry the full key including the `sk-oai-` prefix
* *Wrong authentication method* — OpenShift login tokens are not valid for MaaS authentication; a MaaS API key from the dashboard is required

[NOTE]
====
Distinguish the two authorization errors: *401* (`authentication_error`, "Invalid or expired API key") means the key itself is bad; *403* (`authorization_error`, "Access denied. Your subscription does not have permission to access this model.") means the key is valid but the subscription lacks the model or the authorization policy does not grant your group gateway access.
====

.Fix and revert
Mint a new key using the Module 3 flow: in the dashboard, navigate to *Gen AI studio → API keys*, click *Create API key*, name it, select your subscription, choose an expiration, and click *Create*. Copy the plaintext key (with the `sk-oai-` prefix) — it is displayed only once.

Update the application to use the new key with the same mechanism you used in
Module 4 — patch the `maas-credentials` Secret created in Module 4, Exercise 2 (it lives
in your project), then restart the rollout:

[source,bash,role="execute",subs="specialcharacters,attributes"]
----
oc patch secret maas-credentials --type merge \
  -p '{"stringData":{"MAAS_API_KEY":"{maas_api_key}"}}'
oc rollout restart deployment/maas-chat-client
----

Wait for the rollout to complete, then send a request from the application interface again. It succeeds with `200` — the environment is restored.

[NOTE]
====
Revert verified: the revoked key is gone, the new key is active, and the application pod is `Running` on the updated secret. Nothing else in the environment changed — Module 6 is unaffected.
====

== Exercise 4: Confirm end-to-end reliability

.5 minutes

After restoring from the failure, prove the serving chain is back to its baseline.

. *Re-run the happy path through the application.* Send a request from the application interface and compare the response to the baseline captured in Exercise 1: same structure, `finish_reason: stop`, and a completion consistent with the original — the chain recovers end-to-end after the failure cycle.

. *Verify metrics are still flowing.* Scrape the model server metrics endpoint again and confirm the counters advanced past the values seen in Exercise 2 — through the failed attempts and the recovery, the serving chain kept emitting telemetry:

[source,bash,role="execute"]
----
curl -sk https://localhost:8480/metrics | grep -E 'vllm:num_requests_(running|waiting)|success_total' | head -5
----

Expected output: live metric series with updated counter values.

[NOTE]
====
Metrics still flowing is the handoff to Module 6, where you watch these same series on the observability dashboard while the application generates load. If the counters did not move, revisit Exercise 2 before continuing.
====

. *Summarize the serving chain health.* At this point you have verified:

* Application pod `Running`, sending requests, logging outcomes
* Subscription and authorization policy present; API key valid with `sk-oai-` prefix
* Gateway pods `Running`, routing requests
* Model server `READY`, receiving requests, serving completions
* Metrics flowing from the model server for Module 6

== Module summary

**What you accomplished:**

* Traced a request through the serving chain and verified each component.
* Troubleshot a simulated failure — an invalid API credential.
* Confirmed end-to-end reliability against the baseline.

**Key takeaways:**

* End-to-end validation confirms that deployment, serving, access control, and application integration are all working together.
* Tracing a request through the serving chain reveals where failures occur when something breaks.
* Structured troubleshooting — checking logs at each layer — is essential for maintaining production AI services.
* Keep request payloads under roughly 3.8 MB through the MaaS gateway: oversized bodies fail with an opaque HTTP 500 and an empty body (RHOAIENG-99765), not a 413.
